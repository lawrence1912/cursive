# PDF 走查：宽表格、长代码行、标题与正文分页（第八节 12）

2026-10-09。macOS 27.0，A4、标准页边距（导出 PDF 的默认值）。被测的是导出 PDF 那条真路径：渲染层交出导出 HTML → 壳侧离屏 WKWebView → `NSPrintOperation` 按 `NSPrintInfo` 分页（`PDFPrinter`）。

## 怎么走的

夹具是现写的英文文档（PDFKit 抽中文会失真，夹具因此全用英文）：一张八列宽表（一列放一条不带空格的长网址、一列放中文、一列放行内代码），一段代码（一行 320 个字符不带空格、一行六十个词），以及一百节「标题 + 正好三行的段落 + 随机几段」——三行的段落撞上 `orphans: 3; widows: 3` 就拆不开、只能整段挪页，标题会不会被留在页底，靠它才稳定撞得上。

导 PDF 走自检的 `CURSIVE_SMOKE_PDF_ONLY`（只导一份、不跑探针 —— 探针会改文档），逐页抽字核对，再用 `pdftoppm` 把页面渲成图逐页看。走查留成了 `shell-swift/check-pdf.py`（接进 `release.sh` 第 2 步），每页的字由壳用 PDFKit 抽出来（`CURSIVE_SMOKE_PDF_TEXT`），不依赖本机装没装 poppler。

## 发现与处理

| 走查项 | 改之前 | 原因 | 处理 | 改之后 |
|---|---|---|---|---|
| 宽表格 | 右边两列整列消失，第三列只剩半截；**整份文档被等比缩小着印**（同一份夹具 16 页小字，改完 26 页正常字号） | 一条不带空格的长网址让那一列最窄也得有一整条网址那么宽，表格比纸宽：纸上没有横向滚动条，WebKit 一边裁、一边为了迁就它缩小整页 | 导出时给格子里的长串（≥ 25 个非空白字符）插可折点 `<wbr>`：贪心地切，每截不超过 24 个字符，优先断在 `/ . _ - ? & = # : , ;` 后面（`render.ts` 的 `breakable`）。屏幕上的 HTML 长相不变 | 八列都在纸上，网址在斜杠处折成五行，字号正常 |
| 长代码行 | 正常折行 | `pre code { white-space: pre-wrap; word-break: break-word }` 早就在 | —— | 一个字符不少 |
| 标题与正文分页 | 随机种子 1：**四页以标题收尾**（种子 2 三页）；后面跟的是拆不开的三行段落时 | WebKit 只在后面那块拆得开时才守 `break-after: avoid` | 标题自己不许拆（`break-inside: avoid`），底下挂一块 4em 高、用负外边距抵掉高度的看不见的占位：页底剩下的地方装不下「标题 + 至少几行」，标题就整个挪到下一页；版面上一个像素都不多 | 三个种子都是 0 页 |
| 标题 + 紧跟的表格 / 独图段落 / 块级公式 / mermaid | 那几样整块搬页（`break-inside: avoid`）时，标题照样被留在页底，底下一大片空白 | 同上：整块搬的那一块拆不开 | 渲染层把这一对包进 `div.keep`（同样不许拆）：只包顶层，屏幕上这层 div 没有任何样式 | 标题跟着它走 |

**没修成、留作已知限制**：比一页还长的表照样会在一行的中间断开，断开处也不重画表头 —— WebKit 不守 `tr { break-inside: avoid }`，`thead { display: table-header-group }` 在行中间断开时也不起作用。两条都留在样式表里：导出的 HTML 拿到别的浏览器里打印时它们是有效的。

**顺带看到的**：poppler 对导出的 PDF 报 `Bad 'Length' attribute in stream`，出在内嵌字体程序流上（字典里只有 `/Length1`、没有 `/Length`，字体是系统的可变字体实例），是系统的 PDF 写入器写的；预览、PDFKit、poppler 都能自己修复着读。不在这个应用能改的范围里。

**量法上踩的一个坑**：页码是「`1 / 16`」（中间带空格），走查脚本第一版按 `\d+/\d+` 滤页码，没滤掉，于是每页最后一行永远是页码 —— 「随机种子一处都没撞上」那个结论是测量本身错了，差点据此认定 WebKit 守得住 `break-after: avoid`。拿改之前的代码回跑一遍、看它红不红，是唯一靠得住的证明：`check-pdf.py` 对着改之前的导出代码，「标题收尾」与「宽表格」两条当场红。
