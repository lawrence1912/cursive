# 真实窗口交互基线（第八节 15）

2026-10-09，`python3 shell-swift/measure.py` 连跑三次；被测的应用就是 `04ea021` 的代码（含 ⌃⇥ 的修复 —— 切标签那一项靠真按键 ⌃⇥，没有这个修复根本切不过去）。

## 设备与规模

- **设备**：MacBookPro18,3（Apple M1 Pro，32 GB），macOS 27.0（26A428），内建屏 2×，**60 Hz**（rAF 间隔中位数 17ms；WKWebView 在这块 ProMotion 屏上跑的是 60）。窗口 1080×720，可见且拥有焦点。
- **文档**：第四节红线三的那份规模 —— **10002 行 / 285,680 字**，50 个块级公式、10 张图、43 张表、65 个代码块，带 front matter；另有 5 份同样大小的副本给多标签用。
- **背景**：其他应用都在，但没有人操作；防锁屏的守护每 30 秒在鼠标原位发一个零位移事件。

## 怎么量的

| 量什么 | 口径 |
|---|---|
| 键到帧 | 真按键（`ime-driver` 发 CGEvent，与真键盘同一个入口；自检带 `CURSIVE_SMOKE_KEYS=1` 放行）。起点是 keydown 的 `timeStamp`（WebKit 取平台事件的时刻），终点是下一帧交出去之后：rAF 回调里挂一个 `setTimeout(0)`，它在这一帧的布局、绘制做完之后才轮到。**它天然 ≥ 一个帧边界**，所以「超过 16.7ms 的比例」恒为 100%，不当掉帧看 |
| 同步事务 | 这一下引起的 `view.dispatch` 同步耗时之和（状态 + 装饰 + DOM 写入）。**超过 16ms 的比例才说明这一键在主线程上吃掉了一整帧** |
| 场景 | 打开后的头 5 键（冷）；预热后普通段落 60 键；中文输入法（微信输入法）连打 8 个词约 60 键；开着查找（「正文」，约 4000 处命中）40 键；表格单元格 40 键；以上都在文档中部。键距 100ms（输入法 80ms），约每秒 10 键 |
| 切标签 | 三个标签（两份万行 + 一份小文档）之间真按键 ⌃⇥ 二十次。⌃⇥ 是原生菜单项，页面收不到 keydown，起点改成壳把菜单动作转进页面的那一刻 |
| 滚动 | 每帧把 `scrollTop` 推 40px，推 360 帧；两遍（第二遍 widget 高度都量过了），记 rAF 间隔 |
| 冷启动 | `CURSIVE_TIMING=1` 的「文档进编辑器」「文档已上屏」，自进程启动起算，三次 |
| 导出 | 渲染层交出整份 HTML（1.33 MB）为止，三次；写盘在壳侧，另算 |
| 内存 | `footprint`：应用 + WebKit 的 GPU / WebContent / Networking 三个进程。1 → 3 → 6 个标签，各自稳 3 秒后隔 2 秒采三次取中位数；**排在打字、滚动、导出这些大量分配的测量之前**（第二次就量到了 GC 前的峰值，3 个标签比 6 个还多两百兆） |
| 闲置 CPU / 能耗 | 36 秒里页面上什么都不发生（探针也停下指令轮询 —— 第一次没停，那每 40ms 一次的 IPC 把闲置抬到了 7.6%）；能耗是 `top` 的 POWER（能耗影响，无量纲），闲置一段、逐帧滚动一段 |

WebKit 的计时精度是 1ms，表里的毫秒都是整数。

## 读法

1. **普通打字守得住**：一万行上每键同步 13–15ms，没有一键超过一帧；键到帧中位数 23ms、p95 33–40ms。同步这一项与 2026-10-04 检查报告在真 WKWebView 里派 30 次事务量到的「连续编辑 14ms」一致；第四节红线三记的 0.2.x 基线（1.07 万行 6.3ms）是另一种口径，这里算的是一次按键引起的**全部** dispatch 之和，两者不能直接比。
2. **最该先优化的是「开着查找时打字」**：每键同步约 29ms，键到帧 p95 72ms，三次一致。几千处命中的文档里，每改一个字，状态栏与面板的计数（`searchStat`，缓存按「正文 + 查询」记，正文一变就整份失效，在 dispatch 里同步重扫）和滚动条上的命中刻度（`scroll-marks`，`docChanged` 就在测量阶段重扫，算在帧里）都要把全文再走一遍。下一步：先在单测里把这两笔拆开量，再决定是增量还是降频。
3. **第二是表格单元格里打字**：每键同步约 30ms。疑点在 `writeCell` 之后整张表的重取（`tableDataAt`）与块级装饰的重建；同样先拆开量。
4. **中文输入法的键到帧 ~42ms，但同步只有 4–5ms**：差的那三十多毫秒是输入法自己的往返（keydown → 输入法进程 → 标记文本回到 WebKit），不在我们的代码里。
5. **切标签 ~78ms**：一万行文档的 `setState` 加装饰整份重建，可以接受，留着看。
6. **滚动很稳**：60Hz 下 p95 19ms，慢帧 0–0.3%；首遍偶有一帧 100ms 上下（图与公式第一次渲染）。
7. **冷启动** 一万行文档约 1.0s 进编辑器、1.12–1.15s 上屏；**导出** 1.33 MB 的 HTML 约 50ms。
8. **闲置 2.6%** 不算高也不算零：WebContent 那 1.6%（窗口在前台、光标在闪）与应用进程那 0.9% 都还没拆开看。不急，记着。

写在 `shell-swift/measure.py` 的 `BUDGETS` 里：三次里最差的 p95 约 1.5 倍，取整到好记的数 —— 宽到不被一次系统抖动误伤，窄到一次真的退化一定越线。脚本拿它比，超了退出码 1。

**不进 `release.sh`**：计时类断言在有人用着的机器上随机红，红一次分不清是代码慢了还是机器忙（第三节「E2E 上 CI」同一条理由）。改动碰到编辑器热路径、装饰、查找或表格时，手跑一次：

